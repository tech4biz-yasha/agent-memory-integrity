What this means

Nothing the attacker does to this store reaches the agent. The eight record edits are refused for the same reason as in the default layout: each object carries a hash over its own fields and the order comes from an Ed25519-signed commit chain. The difference is the ninth edit. With the keys and the memory head moved out of the state directory, a store put back to an earlier copy of itself no longer matches the head the server holds, and the read refuses rather than serving the older state as current. Same store, same version, one deployment choice: this row and the default row differ on that cell and nowhere else.

A verdict is what the tool did, not an opinion. "Accepted" means it loaded the altered store, raised nothing, and the agent carried on from the altered memory as if it were true. Every cell has a control that proves the edit landed before the verdict counts.

Where the attacker stands

The attacker reads and writes the Verax state directory beneath the MCP server, as a mounted volume, a shared disk or a restored backup would allow. He signs nothing and he cannot reach the keys directory, which sits outside the state directory under VERAX_KEYS_DIR. An attacker who can reach either is a different measurement and this row does not speak for it.

Reproduce this row

Everything runs offline. The run seeds a fresh store, applies each edit beneath the server's own API, reopens the store and records what memory.get returned.

pip install agent-memory-integrity
mkdir pin && cd pin && npm init -y && npm install @verax-ai/body@0.8.2 && cd ..
export AGMI_VERAX_DIR=<that pin directory>
python agmi/full_runner.py --json results/scorecard.json   # every row, this one included
python -m agmi.agent --target verax-memory+head-outside --families at-rest
