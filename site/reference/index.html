Agent Memory Integrity

Does your agent's memory notice when someone changes it?

13 of the 13 rows that make no integrity claim served every applicable edit as genuine. 27 agent memory and checkpoint stores, 41 rows, seeded through their own APIs, edited behind their backs ten ways, and asked to read their memory again. The 21 that claim tamper evidence were measured against that claim, with the detection point named.

The problem in three frames

01

An agent remembers

Facts, decisions and checkpoints go into a store: a SQLite file, a Postgres table, a vector index, a cloud service.

02

Someone edits the store

No keys, no API: a mounted volume, a shared database credential, a restored backup, a data-plane role. One record changes.

03

The agent believes it

It reads the store the way it always does and acts on the edited memory as its own. agmi measures whether anything in that read, or in a later audit, notices.

How one cell is measured

Seed through the tool's own API, apply one edit behind its back, reopen the store the way its users would, read through the tool's own read path, record what it said. Three controls run before any verdict counts.

The method

The memory agent

Beyond the fixed scorecard, agmi ships an agent that hunts: point it at one store and it searches six attacks, three channels and the content mutations for the first that gets a false memory served as trusted, proves the landing against a positive control, and hands back a reproduction script. Against every real store measured it walked in on the first attempt; only the defended reference store made it search. It runs behind an authorisation gate that fails closed. How it works.

Five levels a store can claim
